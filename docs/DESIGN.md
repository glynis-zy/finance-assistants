# 设计原则与设计模式

> 本文件回答面试最可能被拷问的三个问题：设计原则是什么、用了哪些设计模式（在哪）、系统怎么扩展。
> 每个落点都对应 architecture.md 的分层与 requirements.md 的口径，可实现后逐条 `goto` 验证。

---

## 1. 设计原则

### 1.1 结论由规则引擎拍板（立身之本）
报销合规、预算偏差、应收风险三处结论**只由确定性引擎产出**（`domain/risk_engine`、`deviation_engine`、`scoring_engine`）。LLM 只做：扫描件字段结构化提取（Pydantic 校验）、科目推荐规则盲区兜底、报告润色。**任何结论判定路径上没有 LLM**——同一**结构化解析结果快照** + 同一**规则参数版本**，规则引擎必须产出相同结论，可复现、可审计。这是对 2.7"风险结论永远由规则引擎决定"的继承与扩展。

### 1.2 单一职责（SRP）
路由层只做三件事（收参、调服务、回响应）；服务层一个 service 一个领域（报销/预算/应收/共享基础各司其职）；引擎层只做判定，不含 IO 与 LLM。

### 1.3 开闭原则（OCP）——三处"加配置不改代码"
| 扩展点 | 机制 | 新增成本 |
|---|---|---|
| 规则/校验项 | `risk_engine.REGISTRY` 注册表 | 注册一个 `check_xxx(ctx)` 确定性函数 |
| 偏差/阈值/权重 | `sys_param` 参数表 | 改参数，运行时生效，带审计 |
| 外部厂商（OCR/LLM/Webhook） | `clients/*` 适配层 + `.env` | 只改环境变量 |
| 单据类型 | `document_schemas/` 元数据 | 加一份配置，平台零改动 |

### 1.4 依赖倒置（DIP）
业务代码依赖 `clients.ocr.OCRClient` / `clients.llm.LLMClient` / `clients.webhook.Notifier` 统一接口，不依赖具体厂商 SDK。换百度→阿里、DeepSeek→通义、钉钉→飞书，只动适配层实现与 `.env`。

### 1.5 关注点分离（四层流水线）
报销审核：`OCR 看懂 → LLM 理解 → 规则引擎判定 → LLM 润色`。每层只干一件事，判定层与 IO 层不耦合，可独立测试。

### 1.6 fail-closed（存疑即人工复核）
任一关键校验无法判定（字段缺失、OCR 置信度低、规则异常）→ 结论不得为「通过」，一律「人工复核」。财务系统**绝不"放行存疑"**。退回理由必须可追溯（哪项校验、实际值/参考值/阈值）。

### 1.7 Redis 仅 broker，状态与结果全落 DB
Celery 只把任务传到 worker；任务状态、结论、预警、投递记录全部落 DB。Redis 重启不丢已产生的分析结论。相比 2.7 进程内队列（单进程 Demo 边界），这是**工程化异步边界**：多 worker、可重试、失败可查（仅凭 Celery + Redis 不构成完整生产级，部署/监控/容灾不在 V1 范围）。

### 1.8 单一权威来源（台账）
支出台账是实际支出的唯一权威流水，报销审核通过时写入，预算监控只读。三助手不得各自维护预算/台账副本——预算检查与预算监控读同一份数据，偏差才有意义。

### 1.9 纵深防御（三层权限）
RBAC（能不能做）→ 数据权限（能看哪些行）→ 状态权限（什么状态能做什么）。任何一层不过即拒绝。

### 1.10 最小必要依赖
不引 Vue/构建链、不引重型 ML/统计框架；统计信号用轻量实现。中间件越少越可解释。

### 1.11 可测试性
三个引擎都是**确定性纯逻辑**（无随机、无 LLM、无 IO 依赖，可读 DB/配置），配 pytest 可单测；依赖全部 `Depends` 注入，冒烟测试 `TestClient` 全链路断言。

## 2. 设计模式（克制地贴标签）

> 面试建议：模式名点到为止，多讲"职责是什么、为什么这样拆"，比贴一堆标签更不容易被追问打穿。

### 2.1 明确使用的模式

| 模式 | 落点 | 一句话 |
|---|---|---|
| **策略模式** | `risk_engine.REGISTRY`、`scoring_engine` 评分因子、`deviation_engine` 统计信号 | 规则/因子/信号都是策略注册表，新增=注册一个函数，调用方零改动 |
| **适配器模式** | `clients/ocr`、`clients/llm`、`clients/webhook` | 外部厂商封装成统一接口，换厂商只改适配器与 `.env` |
| **模板方法** | `parse_pipeline`、`deviation_service` 对比流水线、`scoring_service` 评分流水线 | 固定骨架（解析→校验→判定→结论）+ 可替换阶段，各助手复用同一编排 |
| **工厂/注册表** | `parse_pipeline.recognize_document_type`、引擎注册表 | 按文档类别路由解析路径；按维度聚合规则上下文 |
| **责任链** | perms(L1) → scopes(L2) → 状态守卫(L3) | 权限三级校验依次执行，任一关不过即 4xx |
| **装饰器/DI** | `require_perm()` 依赖工厂 + FastAPI `Depends` | 权限作为依赖注入路由签名，接口声明即权限声明 |
| **状态机** | `reimbursement` 状态（待提交/审核中/已通过/已退回/人工复核） | 状态守卫表 + 显式 `_transition`，规模足够，不拆状态类 |
| **单例（懒加载）** | `clients.llm._get_client()`、Celery app | 客户端/任务 app 全局一份，首次调用才初始化 |
| **观察者（借道）** | 预警产生 → `alert` 表 → `notification` 投递 | 预警是事件，站内/Webhook 是订阅通道；诚实标注为"表驱动 + 投递扫描"，不装事件总线 |

### 2.2 有"模式味道"，但不强贴 GoF 标签

| 结构 | 实际是什么 |
|---|---|
| 前端轮询 `/audit-tasks/{id}` | 拉取式状态检查，不是观察者模式 |
| `routers/*` → `services/*` | Controller/Service 分层，service 是业务 |
| services 封装 SQLAlchemy 查询 | Repository 风格：业务不拼 SQL，查询收敛在 service |
| 规则/阈值/权重放 `sys_param` | 配置驱动，不是"策略容器"的过度设计 |

> 诚实的边界：没有用事件总线/消息总线（预警走表 + 投递扫描，规模足够且更可审计）；没有用 ML 管线的模式（当前评分是确定性公式）。被问到就答"按规模选了更简单可解释的方案"。

## 3. 三个助手的判定链（防拷问速查）

### 3.1 报销审核
```
附件 → ocr(发票专用/通用) → llm 结构化提取(Pydantic) → risk_engine 校验(完整性+合规)
     → 科目推荐(规则命中 → LLM 兜底 → 置信度) → 结论(通过/退回/人工复核) → 通过则写台账
```
拷问点：为什么科目推荐用 LLM？→ 规则映射覆盖常规发票，LLM 只在规则盲区给候选、标置信度，未达阈值仍人工复核——LLM 有建议权，无拍板权。

### 3.2 预算监控
```
台账+预算 → deviation_engine(超预算/进度异常/异常增长 阈值) → 统计信号(EWMA/CUSUM/MAD)
     → 多信号或连续 N 期确认 → 正式偏差 → 预警表 → 投递
```
拷问点：为什么阈值还要统计辅助？→ 纯阈值抓不住渐变失控（每月超一点）；统计信号可解释地标"走势异常"，但升级正式偏差仍需确定性确认，保证可审计。

### 3.3 应收预警
```
应收+账龄+账期+付款历史+催收记录 → scoring_engine(账龄40%+账期20%+历史付款30%+催收10%，各因子先归一化 0~100)
     → 0-100 分 → 低(<40)/中(40≤x<70)/高(≥70) → 预计回款日期/预计逾期天数(公式) → 预警表 → 投递
```
拷问点：为什么不用 ML？→ 演示数据无真实历史逾期标签；规则加权可解释可审计，引擎预留模型接口。

## 4. 面试问答预演

**Q: 三个"Agent"之间怎么协作？**
A: 单平台共享基础数据层，不是互相调 API。报销审核通过写台账，预算监控读同一份台账做偏差；应收预警引用共享客户/合同主数据。协作发生在数据层（单一权威来源），不在服务层互相依赖——这比三个微服务互调更简单、一致性与审计都更强。

**Q: 为什么异步选 Celery + Redis 而不是 2.7 的进程内队列？**
A: 3.3 有周期调度（每日预算/应收）与并发任务需求，2.7 的方案是单进程 Demo 边界。升级后 Redis 仅作 broker，任务状态与结论全落 DB——Redis 重启不丢结论，多 worker 可扩展。

**Q: 规则引擎做成注册表而不是 if-else？**
A: ①新增规则只注册一个函数，不碰调用方（开闭）；②每条规则可独立启停/配阈值（策略）；③确定性函数可单测。三个引擎同一套模式。

**Q: 为什么 LLM 不做结论判定？**
A: 财务结论必须可复现、可审计。确定性定义在规则层：同一结构化解析结果快照 + 同一规则参数版本，规则引擎必须产出相同结论；OCR/LLM 解析结果持久化，重放不重调。所以 LLM 只做字段提取（Pydantic 校验）、科目兜底、报告润色，判定永远在规则引擎。fail-closed 兜住所有不确定。

**Q: 预算偏差的"统计辅助"会不会让系统不可审计？**
A: 不会。统计信号只是提示级，不直接产出正式偏差；升级需要"多信号同时成立或连续 N 期"的确定性确认，参数全可配、重跑可复现，正式结论仍是确定性规则产出。

**Q: 换 OCR/LLM/Webhook 厂商要改什么？**
A: 只改 `.env`。适配层封装统一接口（`OCRClient`/`LLMClient`/`Notifier`），业务不感知厂商。

**Q: 台账谁写谁读？**
A: 报销审核结论为通过时在同一事务写台账（另支持导入模拟其他支出源）；预算监控与预算检查只读。单一权威来源，杜绝多份"预算/支出"副本不一致。

**Q: 系统参数为什么放表里不放配置文件？**
A: 管理员要运行时调整（阈值、权重、调度节奏），改表立即生效且带审计；配置文件要重启且无审计。
