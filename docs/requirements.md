## 1. 背景与目标

### 1.1 要解决的问题

财务管理的三个高频痛点：

| 痛点 | 现状 |
|---|---|
| 报销审核 | 发票、行程单、审批单逐单核对，对照报销制度、预算与历史入账，人工耗时且容易漏检 |
| 预算执行 | 部门/项目/费用科目的实际支出偏离预算后难以及时发现，偏差积累到失控才暴露 |
| 应收账款 | 逾期影响现金流，人工跟踪容易遗漏高风险客户，催收缺优先级 |

### 1.2 工具定位

三个助手是**服务型 Agent**：以确定性引擎为骨架，LLM 只在非结构化提取、科目兜底推荐、报告润色处出现。**结论永远由确定性引擎拍板**（可复现、可审计、同一输入同一输出）。

| 助手 | 一句话功能 | 结论产出 |
|---|---|---|
| 3.3.1 发票报销审核助手 | 识别发票/行程单/审批单，校验材料完整性与财务合规性，推荐费用科目 | 通过 / 退回 / 人工复核 |
| 3.3.2 预算执行偏差监控助手 | 按部门×项目×科目×期间对比预算与实际，识别超预算、进度异常、异常增长 | 偏差金额、偏差比例、责任范围、偏差等级 |
| 3.3.3 应收账款逾期预警助手 | 结合账龄、账期、付款历史、催收记录预测逾期风险 | 高风险客户、应收金额、预计逾期时间、催收优先级 |

### 1.3 设计边界

- **单平台 + 三助手**：一个服务承载统一入口与共享基础数据层，三个助手作为模块挂载。
- **本阶段只出设计文档**：本目录五件套（requirements / architecture / tech-stack / dev-standards / DESIGN）+ 根 README，评审通过后再进入实现。
- **演示形态**：单机 Docker 部署（MySQL + Redis + 后端/Celery），seed 演示数据，原生单页控制台。

## 2. 术语表

| 术语 | 定义 |
|---|---|
| 费用科目 | 费用分类维度，如差旅费、办公费、业务招待费，全局统一（共享基础层单一来源） |
| 预算 | 按部门×项目×科目×期间分配的计划支出额度，含月度分摊曲线 |
| 支出台账 | 实际支出的权威流水账，报销审核审批通过时写入；预算监控只读 |
| 报销单 | 员工提交的报销申请，含明细与附件（发票/行程单/审批单） |
| 发票 | 报销凭证，增值税普通/专用发票等 |
| 行程单 | 出行凭证（机票/火车票行程单、打车行程单） |
| 审批单 | 事前审批单据，报销须与审批一致 |
| 应收账款（应收） | 按合同/客户/发票登记的应收回款 |
| 账龄（逾期天数分段） | 按逾期天数分档：未逾期 0 / 1–30 天 / 31–90 天 / 91–180 天 / >180 天 |
| 账期 | 合同约定的回款期限（如月结 30 天） |
| 逾期天数 | max(0, 当前日期 − 合同到期日) |
| 催收记录 | 对客户的催收动作时间线（催收渠道、结果） |
| 实际执行进度 | 截止当前累计实际支出 / 整期预算总额 |
| 计划执行进度 | 截止当前累计计划预算 / 整期预算总额（来自月度分摊曲线） |
| 进度偏差 | \|实际执行进度 − 计划执行进度\| |

## 3. 用户角色与权限

轻量 RBAC，沿用 2.7 项目的三级纵深防御：**角色（能不能做）→ 数据权限（能看哪些行）→ 状态权限（什么状态能做什么）**。

### 3.1 角色与职责

| 角色 | 职责 | 核心权限码 |
|---|---|---|
| 报销申请人 `applicant` | 提交/编辑报销单、查看自己的审核结论 | `reimb:create` `reimb:view_own` |
| 财务审核 `finance` | 审核报销、人工复核存疑单、查看台账与偏差 | `reimb:audit` `reimb:manual_review` `ledger:view` |
| 预算管理员 `budget_manager` | 维护预算、配置偏差阈值、查看偏差与预警 | `budget:manage` `budget:view` `threshold:manage` |
| 应收专员 `ar_specialist` | 维护客户/合同/应收、查看风险排名与催收优先级、登记催收记录 | `ar:manage` `ar:view` |
| 系统管理员 `admin` | 用户/角色/系统参数管理 | `user:manage` `role:manage` `sys:manage` |

### 3.2 数据权限示例

- 报销申请人只能看**自己的**报销单（行级过滤，非前端拼 SQL）。
- 财务审核能看全部报销单与台账。
- 预算管理员能看全部部门/项目预算与偏差；应收专员仅能看应收域数据。

### 3.3 状态权限示例

报销单处于「待提交」时申请人可编辑；「审核中」仅财务可操作（人工复核/退回）；「已通过」状态不可修改（冲销不在 V1 范围）。任何一层不过即拒绝（4xx）。

## 4. 功能需求

### 4.1 共享基础数据（平台底座）

| 模块 | 功能 | 归属 |
|---|---|---|
| 费用科目 | 科目增删改、启停、科目与发票类型/关键词映射 | 共享层 |
| 部门/项目 | 组织主数据、项目主数据（所属部门、负责人） | 共享层 |
| 预算 | 按部门×项目×科目×期间建预算，支持月度分摊曲线（S 曲线）；支持追加/调整并留痕 | 共享层 |
| 支出台账 | 权威流水账；报销审核通过时写入；支持导入模拟其他支出源（采购/工资等） | 共享层 |
| 客户/合同 | 客户主数据、合同台账（金额、账期、执行状态） | 共享层 |
| 系统参数 | 阈值/权重/调度节奏运行时调整，变更带审计 | 共享层 |

> **关键约束**：台账是单一权威来源。报销审核是台账的**写入方**之一，预算监控是**只读方**。三助手不得各自维护预算/台账副本。

### 4.2 3.3.1 发票报销审核助手

#### 4.2.1 输入
- 报销单主信息（申请人、部门、项目、金额、费用明细）；
- 附件：发票（拍照/PDF）、行程单（机票/火车票/打车）、审批单（事前审批）；
- 参照数据：报销制度、预算（预算检查）、历史入账（重复报销检查）、科目映射。

#### 4.2.2 处理流水线（四层）
```
附件 → ① OCR 解析（发票/行程单/审批单）→ ② LLM 字段结构化提取（Pydantic 校验）
     → ③ 规则引擎校验（完整性 + 合规性）→ ④ 科目推荐（规则为主 + LLM 兜底）
     → 结论（通过 / 退回 / 人工复核）+ 报告
```

- **① OCR**：发票专用识别（发票号、金额、抬头、日期、税额）+ 通用识别（行程单/审批单）。识别置信度低于阈值（默认 0.8）记入风险项。
- **② LLM 提取**：对扫描件/非标字段做结构化提取，输出过 Pydantic 校验（禁止自由文本字段）。LLM 失败不阻断链路，降级为"字段缺失"风险项。
- **③ 规则引擎**：确定性规则注册表，见 4.2.4。
- **④ 科目推荐**：优先规则命中（发票类型/关键词/科目映射表），命中不到或置信度低时由 LLM 给出候选科目（Pydantic 校验），仍未达阈值 → 人工复核。

#### 4.2.3 输出
| 输出 | 说明 |
|---|---|
| 审核结论 | `通过` / `退回` / `人工复核`（fail-closed，不确定一律人工复核） |
| 推荐费用科目 | 主推科目 + 置信度 + 候选 |
| 校验明细 | 每项校验的实际值/参考值/阈值/通过否 |
| 风险项列表 | 每项的风险等级 + 处理建议 |
| 审核报告 | 结构化摘要 + 全文（可导出 HTML） |

#### 4.2.4 校验规则清单（规则注册表，均可配）
| 类别 | 规则 | 口径（默认值，可配） |
|---|---|---|
| 材料完整性 | 发票存在 | 至少 1 张有效发票 |
| | 行程单存在 | 差旅类报销必须携带 |
| | 审批单存在 | 预算类/差旅类必须携带 |
| | 金额一致 | 发票金额合计 = 报销金额 |
| | 抬头一致 | 发票购买方 = 本公司（或员工本人，按制度） |
| 财务合规 | 预算内 | 截止当前期间累计台账实际支出 + 本次拟报销金额 ≤ 截止当前期间累计预算（**台账为唯一权威来源**，含采购/工资等其他支出） |
| | 科目合法 | 推荐科目存在且未停用 |
| | 重复报销 | 查重范围 = 已生效 `expense_ledger` + 当前未终结 `reimbursement`，在业务事务内进行查重；`invoice_key` 保留普通索引（**不设全表 UNIQUE**，避免退回/作废单据合法重新提交被永久阻止） |
| | 审批单一致性 | 审批金额一致/不超审批额度、审批项目一致、审批申请人 = 报销申请人（差旅可选：行程日期在审批有效期内） |
| | 超标 | 单笔/单日金额超制度标准 |
| | 日期合理 | 发票日期在允许报销区间（如 180 天内） |

> **V1 关闭**：供应商在册规则在 `risk_engine.REGISTRY` 保留扩展位但默认 `disabled`，V1 不提供供应商主数据维护能力（不建 `supplier` 表）。

**fail-closed 原则**：任一关键校验无法判定（字段缺失、置信度低、规则异常）→ 结论不得为「通过」，一律落到「人工复核」。

### 4.3 3.3.2 预算执行偏差监控助手

#### 4.3.1 输入
- 预算（共享层）；
- 支出台账（共享层，只读）。

#### 4.3.2 处理
按部门×项目×科目×期间分组对比，输出三类偏差 + 统计提示信号：

| 类型 | 口径（默认值，均可配） |
|---|---|
| 超预算 | 截止当前累计台账实际支出 > 累计预算（按核算期间，台账为唯一权威） |
| 进度异常 | \|实际执行进度 − 计划执行进度\| > 阈值（默认 15%）；两者均以**整期预算总额**为分母，计划执行进度来自月度分摊曲线——曲线前重/后重不会误报 |
| 异常增长 | 环比增幅 > 阈值（默认 30%）或 同比增幅 > 阈值（默认 50%） |

**统计辅助信号（提示级，不直接升级为正式偏差）**：
- EWMA：平滑"期望支出率"，捕捉缓慢漂移；
- CUSUM：对持续小幅偏移敏感的累积检器；
- MAD 修正 Z-score / 截面分布：找同类（同科目/同部门）中偏离同侪的离群者。

**升级规则**：统计信号连续 N 期成立（默认 2 期）或 ≥2 个独立信号同时成立，才升级为正式偏差；否则仅提示。

#### 4.3.3 输出
| 输出 | 说明 |
|---|---|
| 偏差明细 | 维度（部门/项目/科目/期间）、预算值、实际值、偏差金额、偏差比例 |
| 偏差等级 | 按偏差比例判级：<5% 低、5%≤x≤20% 中、>20% 高；阈值由 sys_param 配置，可调 |
| 责任范围 | 偏差归属的部门 / 项目 / 科目及其负责人 |
| 进度异常项 | 实际执行进度 vs 计划执行进度、偏离值、统计信号 |
| 异常增长项 | 环比/同比增幅、触发信号 |
| 预警 | 高等级偏差写入预警表并触发投递 |

### 4.4 3.3.3 应收账款逾期预警助手

#### 4.4.1 输入
- 应收账款（共享层客户/合同 + 应收域）；账龄分段；合同账期；客户历史付款；催收记录。

#### 4.4.2 处理（规则加权评分，确定性）
```
风险分 = 账龄档分×40% + 账期因子分×20% + 历史付款因子分×30% + 催收记录因子分×10%
四个因子先各自归一化为 0~100 分，再乘权重求和，总分范围 0~100。
逾期天数 = max(0, 当前日期 − 合同到期日)；账龄按逾期天数分档（非挂账时长）。
预计回款日期 = 合同到期日 + 历史平均回款延迟（规则公式）
预计逾期天数 = max(0, 预计回款日期 − 当前日期)（对外概括为"预计逾期时间"）
催收优先级 = 分档：低 score<40 / 中 40≤score<70 / 高 score≥70
```

| 因子 | 口径（默认值，均可配） |
|---|---|
| 账龄档分 | 按逾期天数分档：未逾期 0；1–30 天 30；31–90 天 50；91–180 天 70；>180 天 90 |
| 账期因子 | 按合同账期长度归一为 0~100（账期越长相对越缓，因子分越低） |
| 历史付款 | 历史逾期次数、平均回款延迟（相对账期的延迟）归一化 |
| 催收记录 | 已催收未回款加分；催收后回款正常减分 |

#### 4.4.3 输出
| 输出 | 说明 |
|---|---|
| 高风险客户排名 | 按风险分降序，附应收金额、账龄、账期 |
| 预计回款日期 / 预计逾期天数 | 预计回款日期 = 到期日 + 历史平均回款延迟；预计逾期天数 = max(0, 预计回款日期 − 当前日期)（对外概括为"预计逾期时间"） |
| 催收优先级 | 高/中/低三档 + 建议动作（如高：立即发起催收） |
| 预警 | 高风险（≥70 分）写入预警表并触发投递 |

### 4.5 预警与消息中心

- **预警表**：统一承载预算偏差、应收风险两类预警（类型、级别、摘要、详情 JSON、产生任务、时间）。
- **站内展示**：控制台"预警中心"面板，未读/已读状态。
- **Webhook 投递（适配器）**：预留邮件 / 企业微信 / 钉钉通道，配置环境变量即启用，未配置降级为仅站内。
- **投递状态**：每次投递记录成功/失败与重试（幂等，不重复投递同一条）。

### 4.6 调度（Celery beat）

| 任务 | 节奏（默认值，可配） |
|---|---|
| 预算偏差监控 | 每日一次（如 08:00） |
| 应收逾期预警 | 每日一次（如 08:30） |
| 报销审核解析 | 事件触发（提交报销单即入队） |

> 所有周期任务结果落 DB，可查最近一次运行时间与状态。

## 5. 非功能需求

| 项 | 要求 |
|---|---|
| 可解释性 | 每个结论可追溯到具体规则/因子/实际值/参考值/阈值 |
| 可审计性 | 全链路审计日志：谁在何时对何单据/参数做了什么，含配置变更 |
| 确定性 | 同一**结构化解析结果快照** + 同一**规则参数版本**，规则引擎必须产出相同结论；OCR/LLM 解析结果持久化，审核重放默认基于已落库的解析快照执行（不重调 OCR/LLM） |
| fail-closed | 存疑即人工复核，绝不"放行存疑" |
| 幂等性 | 重复提交/重复投递不产生重复结果（按单据号/预警唯一键） |
| 一致性 | 台账单一权威来源；预算检查与预算监控读同一份数据 |
| 性能 | 演示规模（万级单据/千级客户）下，每日任务分钟级完成；审核结论秒级（异步队列） |

### 6.2 3.3.1 报销域

## 7. 验收标准

### 7.1 3.3.1 报销审核
- [ ] 提交报销单（发票/行程单/审批单附件齐全）→ 自动解析 → 输出结论、推荐科目、校验明细；
- [ ] 金额不一致/抬头不符 → 结论为退回，风险项列出实际值/参考值；
- [ ] 审批单一致性：审批金额超额度 / 审批项目不符 / 审批申请人≠报销申请人 → 退回或人工复核；
- [ ] 任一关键校验无法判定（如发票 OCR 置信度低）→ 结论为人工复核（fail-closed）；
- [ ] 推荐科目：规则可命中则确定性命中；规则盲区走 LLM 候选并标置信度；
- [ ] 预算检查基于台账：截止当前累计台账实际 + 本次拟报销 > 预算 → 退回/人工复核并提示超支金额；
- [ ] 重复发票被拦截：查重范围 = 已生效台账 + 未终结报销单，业务事务内查重；退回/作废后同一发票可合法重新提交；
- [ ] 审核报告可导出 HTML。

### 7.2 3.3.2 预算监控
- [ ] 按部门/项目/科目/期间输出偏差金额与偏差比例；
- [ ] 超预算、进度异常、异常增长三类分别触发正确（可配阈值）；月度分摊场景：累计实际=累计计划（如 6 月实际=计划 60/120 万）**不报**进度异常；
- [ ] 统计信号（EWMA/CUSUM）连续 2 期成立才升级正式偏差，单期仅提示；
- [ ] 输出责任范围（部门/项目/科目 + 负责人）；
- [ ] 高等级偏差写入预警表并投递（站内必达；webhook 配置后可达）；
- [ ] 同一数据重跑产出同一偏差结果。

### 7.3 3.3.3 应收预警
- [ ] 风险分按账龄/账期/历史付款/催收记录正确计算；
- [ ] 高风险客户（score≥70）进入预警并触发投递；边界值 score=70 归为高风险；
- [ ] 输出高风险客户排名、应收金额、预计逾期时间、催收优先级；
- [ ] 催收记录登记后风险分相应变化（可配置权重验证）。

### 7.4 全链路
- [ ] 报销审核通过 → 台账新增一笔 → 次日预算监控能见该笔支出；
- [ ] 管理员改阈值 → 下一次监控任务生效（参数化，不改代码）；
- [ ] 三级权限逐层校验，越权一律 4xx；
- [ ] 审计日志覆盖：登录、参数变更、阈值变更、预警投递。

## 8. 演示边界与约束

- **Celery 为工程化异步边界**：Redis 仅作 broker，任务状态与结论全落 DB；即使 Redis 重启，已产生的分析/预警不丢。注意：仅凭 Celery + Redis 不构成完整生产级，部署/监控/容灾不在 V1 范围。
- **演示数据**：seed 脚本灌入——4 个部门、若干项目、科目体系、3 个核算期的预算与台账、客户/合同/应收/付款/催收，覆盖三助手各档位结论（通过/退回/人工复核、低中高偏差、高中低风险）。
- **外部服务可降级**：OCR/LLM 未配置 key 时走预设解析结果（`preset`/`auto`/`real` 三模式，沿用 2.7 约定），演示链路始终可跑。
